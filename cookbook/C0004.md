# C0004 — A slow gate is a bug: parallel worktrees, a per-binary lock, the parallel flag on every build
tags: gate,parallel,worktree,lock,build,throughput · date: 2026-10-03 · phase/task: - · origin: decomp-architect

A gate that takes tens of minutes per binary is a defect to fix, not a cost to absorb. Drafting is cheap and parallel, but
the byte gate is where a campaign's wall-clock goes. The byte gate is a build and a hash per draft.

**Why:** on the source project one binary's gate ran for an hour while thirty-seven finished drafts queued behind it. Sixteen
binaries were once gated serially to protect one carving job. That took an hour for what the parallel form did in minutes. A
single binary's build without `-j` was measured six times slower than with it, byte-identical either way. The gate had been
believed to cost forty to sixty minutes, but clean, it cost fifteen seconds. The stalls were bisects.

**How to apply:** parallel is the default. Each binary gates in its own worktree under a per-binary lock. The worktree gives
isolation: a carving worker writes only inside its tree. The lock gives mutual exclusion: two lanes never gate the same
binary. Every tool that shells a build passes the parallel flag. A bad parallel build fails the hash, and it cannot bank
wrong bytes.

Batch the expensive population behind a strong pre-filter. On failure, bisect. Merge carve state so two workers never clobber
each other: adopt per-binary files whole and splice a shared registry by block. If you find yourself writing a serial loop
over binaries, stop. That is the hour-long mistake.
