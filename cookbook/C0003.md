# C0003 — Offline tooling first: every computable step becomes a zero-token deterministic tool
tags: strategy,deterministic,recovery,permuter,economics,tooling · date: 2026-10-03 · phase/task: - · origin: decomp-architect

When a recovery, diagnosis or integration step is computable, it belongs in a deterministic tool. That tool runs with zero
tokens on every future draft. The step does not belong in an agent prompt and it does not belong in a search.

**Why:** the measured economics kept pointing the same way on the source project. A fifty-agent wave once added a third of a
percent while deterministic recovery added nearly three points for about no tokens. The permuter's problem turned out to be
targeting, not a missing transform. Most of its CPU was aimed at residuals that a search provably cannot close, and a
deterministic classifier fixed that for free. Every hour of agent drafting is spent once, but every deterministic stage is
spent once and paid forever.

**How to apply:** keep the two engines separate. One engine is deterministic recovery: declaration, arity and cast
reconciliation, type lifts and carve repairs. These are computable fixes, applied always, and the byte gate arbitrates them.
The other engine is search: the permuter, for register and schedule permutations where the answer must be explored. Putting a
computable fix into the search is a category error.

When a draft fails to bank, ask "is this residual computable?" before you reach for agents or the permuter. If yes, add a
stage. For that stage, check whether the logic already exists in another tool (one implementation, many callers). A stage
that mutates shared state undoes by snapshot-restore, never by an inverse transform, and is verified fleet-wide. Track the
model-free fraction of the work. Make raising it the objective.
