# C0294 — Load hoisted above a byte store by sched1: fence the store in do { } while (0)
tags: codegen,sched,sched1,hoist,load,store,do-while,loop-notes,fence,FAKE · date: 2026-11-01 · phase/task: 3.4/T15 · origin: W80 FB6F4_ovl04

symptom: a byte store is followed by a load from the same object. The target loads after the store (`li 4; sb 5(obj); lb 2(obj)`). Ours hoists the `lb` above the `li` and the `sb`.

cause: sched1 moves the load above the store, because the two addresses do not overlap. A volatile read, a moved read and an `s32` local do not stop it. A `do { } while (0)` puts loop notes around its body. Then sched1 does not move insns across the notes.

lever: fence the store, not the load. Write `do { obj[5] = 4; } while (0); // !FAKE:`, then the plain read `s = ((s8*)obj)[2];`.

## Instance
W80 rockx5 func_800FB6F4_ovl04 (c18) matched at try 7. Try 2 had 3 words of diff, and the residual was the hoisted `lb`. A fence on the read (`do { s = obj[2]; } while (0);`) took the diff to 2 words, but it moved `sb 3` before `li 12`. This is one datapoint.
Near: C0275 (a `goto` stops a sched1 hoist), C0284 (one shared local stops a sched1 hoist).

## Extension: a fence that fixes the registers (W85)
W85 slus func_8005748C (c22) is a fourth datapoint, and the fence fixes regalloc, not sched. Write `do { *(u16*)(obj + 0x14) = t - 1; obj[0x16]--; } while (0); // !FAKE:`, with the `s8` test of the byte after the fence. The decremented byte then lives across a block boundary. Local-alloc gives `t - 1` the `$v0`, and the byte takes `$v1`.

A fence on the u16 store alone fixed the registers, but it stopped the sched2 hoist of the `lbu`.
W85 slus func_8001D580 (c45) is a fifth datapoint. Write `do { name.s.b[2] += idx; } while (0); // !FAKE:`. Then sched1 does not move `li 30` and `li -1` into the `lbu` delay slot.
Riders (T20.c50, `harvest.py rider`, strip = no fence): load-bearing on slus func_8005748C and func_8001D580 (banked W85).
