# C0149 — Unboostable hard-reg arg set: a zero-store after an aliasing load opens its sched slot
tags: codegen,sched,delay-slot,arg-reg,store-order,boost,zero-store · date: 2026-10-19 · phase/task: 3.2/T3 · origin: .run/p32t3/c28 (W23 harvest)

symptom: an arg reg set (`li $a1,0`) lands in a branch delay slot, but the target has it mid-block
lever: sched store-free window

## Residual
rockx5 func_800F0DAC_ovl02 (W21 draft, diff 8 of 168). Ours had `a1=0` in the `beqz` delay slot. The target has it in place of `li $v0,0x2D`.

## Mechanism
Pass group `sched`. sched1 never boosts a hard-reg arg whose reg has REG_N_SETS > 1. Here `$a1` is set in both arms (0 and 5).
The set loses every latency tie to stores (potential hazard) and to boosted defs. So it drifts to the top of the block, and reorg puts it in a delay slot.

It is scheduled only in a cycle with no store and no boosted def ready. One such cycle: right after an aliasing load (`lbu` of a global the stores may alias), when the memory unit blocks the next store.
If the last store before that cycle is a zero-store (`sw $0`, no value def pending), the arg set wins the slot. Diagnosed with `cc1 -dS -dR` (.run/p32t3/rockx5_func_800F0DAC_ovl02/).

## Lever
Move constant-zero field stores (`e->unk67 = 0; e->unk68 = 0;`) to be the first stores after the aliasing load (`e->unk14 = D_8009A0A0.bg_offset;`).
Near C0051 (tie order) and C0052 (birthing boost). Neither applies, because the arg cannot be boosted.
