# C0186 — Byte global copied among byte stores: write the copy first, char stores alias it
tags: codegen,sched,alias,load,store-order,u8,global,char · date: 2026-10-24 · phase/task: 3.3/T16 · origin: W38 slus 8004FC64

symptom: a byte global is copied into a new object's field among a run of byte field stores. Ours loads the global (`lbu`) late, after the byte stores. The target loads it early and stores it late.
cause: char stores may alias a char global. So gcc cannot hoist the global's load above them. The scheduler can still sink the field store.
lever: write the copy (`obj->bg_offset = D_8009A0B4;`) before the aliasing byte stores in source. The load lands where the target has it, and the scheduler pushes the store down.

## Instance
W38 slus 8004FC64: the copy after `state/unk5/unk6 = 0` gave 39/48 diff words. The copy before them matched. It is the likely lever for W38 EFAC4_ovl09 (same 0x14 <- D_8009A0B4).
Related: C0051 (statement order), C0060 (load stuck below a store), C0178 (read into a local where the target loads it).

## Extension: an arg byte read before aliasing stores (W40)
The same barrier holds for a read of an argument byte or a table. Read it in the source before the byte or half stores where the target loads it early.

W40 slus 4EB7C: `obj[0x54] = p[7]` before the 0x16 and `[4]++` stores matched. W40 F1A2C_ovl07: `tmp = table[arg0[2]]` before `p[0x47] = 6` matched. Riders (T18.c50, strip = the read moved after the stores): load-bearing on both.
