# Owner of a pointer into same-vram overlays
Problem: several overlays share one vram. The value of a data word does not tell which overlay it points into.
- Nearest-symbol naming picks an arbitrary member (`gcc2_compiled`, `ovlNN_VRAM` for the region base). (2.4/T1)
- Static residency ("load would not overwrite the site") is not owner evidence. A runtime load trace showed that most such targets lie in the site overlay's own span. (2.4/T3.1)
- A dispatch table indexed by object type has no stage-index owner. The owner of each entry needs a per-type spawn trace. (2.4/T3.1.1)
- Forcing a spawn under each candidate overlay and checking a balanced return at the dispatcher's jalr discriminates. A forced read alone only restates residency. (2.4/T3.1.1.1)
- Sharper: the overlay that spawns a type (static jal-allocator + type-store search) names the owner. A forced call is often "ok" in a wrong overlay. Call counts are not evidence (the wrong overlay ran 7x more). (2.4/T3.1.1.1.1)
- A forced poke of a selector reads the table word under any resident. Only faulting after the jump discriminates, and it can exclude every candidate. (2.4/T4.1.1)
Undecided words stay raw/allowlisted, never guessed.
