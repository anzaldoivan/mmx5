# C0187 — Global s16 load hoisted above stores: declare it s16[] and read [0], not a scalar
tags: codegen,alias,scalar,array,extern,lh,hoist,load-order · date: 2026-10-24 · phase/task: 3.3/T16 · origin: W38 FB148

symptom: a global s16 is read as a call argument after a run of field stores. Ours hoists its `lh` above the stores. The target loads it after them.
cause: as a scalar `extern s16 X;`, the symbol cannot alias the stored object, and gcc's alias analysis knows it. So the load moves up. As an array the symbol may alias, and the load stays after the stores.
lever: declare `extern s16 X[];` and read `X[0]`.

## Instance
W38 FB148_ovl41: `D_800FB784_ovl41` as a scalar hoisted the lh. As `s16[]` read at `[0]`, the lh stays after `sh 6(s0)` and the function matches.
Related: C0060 (load stuck below a store: the opposite direction), C0186 (aliasing pins a load).
