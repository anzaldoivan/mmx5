# C0278 — Byte table column loses andi 0xFF: post-increment the column field inside the index
tags: codegen,andi,0xff,u8,post-increment,index,table,combine · date: 2026-10-31 · phase/task: 3.4/T8 · origin: W73 EED30_ovl12

symptom: a byte table row is read with a byte field as the column, and the column field is then incremented. The target keeps an `andi 0xFF` on the old column value. Ours drops the `andi`, or loads the field twice.

cause: an increment on its own line makes a second statement. Then combine knows the loaded value is a `u8` and drops the mask. A post-increment inside the index keeps the old value and the new value in one expression, and the `andi 0xFF` stays.

lever: write the post-increment inside the index: `obj[5] = D[obj[0x86]][obj[0x87]++];`. Do not write `obj[0x87]++;` as a separate statement.

## Instances
W73 rockx5 func_800EED30_ovl12 (c17): the post-increment index took the diff from 17 to 14 words, then a store-order fix matched.

W73 rockx5 func_800F4AF4_ovl03 (c32) matched at try 1 with `D_800FA0BC_ovl03[o[0x92]][o[0x93]++]`. W73 rockx5 func_800F36A8_ovl09 (c31) matched the same table read at once, but that target failed on other words.
