# C0333 — Table byte loaded after a zero store: read it into a u8 local before both stores
tags: codegen,sched,u8,local,load,store,table,store-order,lbu · date: 2026-11-07 · phase/task: 3.4/T29 · origin: W94 FC93C_ovl39 F872C_ovl00

symptom: a byte is read from a table and stored to a field next to a zero store. The target loads the byte first, then stores 0. Our build stores 0 first.

cause: with the table read inline in the store, the load stays below the zero store. A `u8` local set before both stores makes the load a separate insn. Sched can then put the zero store after the load.

lever: read the table byte into a `u8` local before the stores. Then write `obj[6] = 0; obj[5] = t;`.

## Instance
W94 rockx5 func_800FC93C_ovl39 (c5) and rockx5 func_800F872C_ovl00 (c18) matched at try 2. Both write `t = table[...]`, then `obj[6] = 0`, then `obj[5] = t`. The store order alone is inert. Swapping the two stores after the local gives the same bytes.
Near: C0234 (store order), C0060 (load below a store).

## Byte proof
Riders (T29.c50, `harvest.py rider`, strip = no local, the load inline in the 0x5 store): load-bearing on rockx5 func_800FC93C_ovl39 and func_800F872C_ovl00 (banked W94).
